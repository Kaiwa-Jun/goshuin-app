# Issue #320: 写真の無い有名な寺社（rank 5 の 150 件）に、帯の写真を足す（#302 第2弾）

## 概要

#302 で地図のピンのシートの帯に 688 寺社の写真を出した（本番に反映済み・1.2.0 が読む）。写真の無い寺社のうち、いちばん有名な rank 5 は 469 件中 150 件。ここを、**データだけで**埋める（アプリのコードは変えない）。

1. **結べていない寺社を手で結ぶ**: #301 の対応表で `none` / `low` の 50 寺社は、対応表を作り直さずに、リーダーが Wikidata の項目を 1 件ずつ確かめ、機械で確かめられる根拠（名前・距離）つきの小さな公開の台帳 `supabase/data/spot-wikidata-manual-320.json` に入れる（D-3）
2. **写真の出どころを P18 の外に広げる**: Commons のカテゴリ（P373）の直下のファイルと、構造化データで「描かれているもの P180 = その Q-ID」のファイル（手で結んだ寺社は P18 も）を集め（D-4）、第1弾と同じ `screenFile` で絞り、1 寺社 30 ファイルまでの公開の候補 `supabase/data/spot-photos-320.json` にする（D-5・D-6）
3. **リーダーが選ぶ**: 第1弾の選ぶ画面を第2弾の候補でも使えるようにし（D-7）、選んだものを台帳 `spot-photos-302.json` に `batch: 2` で足す（第1弾の行は変えない。D-8）
4. **本番に入れる**: 第2弾の分だけの migration と確かめる SQL を新しいファイルで作り（D-9）、R2 にはオーナーが新しい分だけを置き、データベースにはリーダーが入れる（D-10・「本番」）

## リスク・不確実な点／申し送り

- **手で結べる数**: #301 のキャッシュだけで規則を通るのは 17 / 50。残りは Wikidata に項目が無い・P625 が無い・seed から 3km より遠い（奥宮・山上の社など）ものがありうる。結べなかった寺社は `gap: 'no-qid'` で残り、`progress.md` に理由を書く
- **候補の質**: カテゴリの直下には、仏像・御朱印・祭り・地図・古い絵葉書・内部の写真も入る。P180 は付いていない寺社が多い。採れずに外す数が第1弾より多くなりうる（第1弾は 733 中 45 を外した）
- **同じ境内の別の社**（戸隠神社 3 社・伊勢神宮の内宮と外宮・金刀比羅宮と奥社 など）: カテゴリや項目が同じか重なり、別の社の写真を採りうる。AC-23 で同じ `qid` / P373 の行を全部見る
- **候補のファイルの大きさ**: `spot-photos-320.json` は 150 寺社 × 30 ファイルまで（HTML なしで 1 ファイル 0.5KB 前後）。最大で 2MB 前後の公開のファイルになる
- **Commons の負荷**: 一覧と imageinfo（extmetadata つき）で数百回。`maxlag` や 429 で止まったら同じコマンドで続きから。待ち時間を延ばすのはリーダーの判断
- **すぐ利用者に出る**: 第1弾と違い、H-9 でアプリ（1.2.0）に写真が出る。選び間違いは `withdrawn` で外す（戻すとき）
- **ユニーク変換の数**: 帯の写真は最大 688 + N2（≤ 838）/月。御朱印の 1200 / 400 と合わせて月 5,000 を超えるかは、Cloudflare の Images の使用量で月に一度見る（第1弾と同じ）
- **SQL の大きさ**: 第2弾は 150 行以下で 60KB 前後の見込み（第1弾の約 274KB は通った）
- **撮影者の文字**: 第1弾の決定 8 のとおり Commons の表示のまま（`No machine-readable author provided…` もそのまま出る）
