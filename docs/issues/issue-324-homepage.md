# Issue #324: ホームページ goshuinsanpo.com を作る（アプリの紹介と、寺社ごとのページで検索から人を呼ぶ）

## 概要

集客の計画（2026-10-10、オーナー了承）の施策 E。実際の利用者は 6 人で、入口がほぼ App Store の検索だけ。ストアの外の入口として、Google の検索と AI の回答（AIO）から人を呼ぶホームページを `goshuinsanpo.com` に作る。狙う人は 20〜30 代の女性の御朱印好き。訴える一言は「参拝したら、写真1枚で日本地図に。」（2 本目「家にある御朱印帳も、まとめて地図に。」）。

1. **置き場所**: このリポジトリの GitHub Pages を GitHub Actions で出し、独自ドメイン `goshuinsanpo.com`（`www` は `goshuinsanpo.com` へ）にする。ソースは新しい `site/`、生成器は Deno（外部のフレームワークを足さない。テンプレートは TypeScript の関数）
2. **ページ**: ① トップ（アプリの紹介・スクショ 4 枚・App Store へのバッジ）② 寺社ごとのページ `/spots/<slug>/`（**777**。写真のある寺社だけ）③ 都道府県ごとの一覧 `/prefectures/<ローマ字>/`（47）④ アプリのプライバシーポリシー・利用規約（今の文・今の URL）と、このサイトのプライバシーの説明
3. **検索と AI**: `sitemap.xml`・`robots.txt`・canonical・OGP・JSON-LD・`llms.txt`。事実と出典が分かる文だけを載せる
4. **計測**: Cookie を使わない Cloudflare Web Analytics
5. **アプリのコードは変えない**（`src/` などに差分を作らない）

## テスト方針

- 生成器は**純関数**にして Deno のテストで確かめる（TDD）: slug の台帳・受付時間の読み方・`formatHours`・ページを作るかの判定・近くの寺社・地図のリンク・App Store の URL・JSON-LD・sitemap・robots・llms.txt・HTML の逃がし・beacon の有無・出さない語の検査・生成物の検査（`check`）
- 本物のデータでのテスト（`data_test.ts` の形）: 本物の seed・台帳・受付時間の seed から数と標本を確かめる。数は**入力から計算した値**と比べる（台帳の approved の数 = ページの数、など）。いまの値（777・332・410・6 など）はこの契約に書いた
- 生成物は `check` と evaluator（Playwright・Lighthouse）で見る
- テストはネットに出ない（写真の URL は文字として比べる）

## リスク・不確実な点／申し送り

- **「受付時間」で検索する人にはほとんど答えられない**: 受付時間があるのは 8 寺社（seed の 12 行のうち御朱印と明記された分）だけで、777 ページの大半は写真・住所・地図のリンク・近くの寺社だけ。Issue の「〇〇神社 御朱印 受付時間」には 8 寺社しか当たらない。受付時間を増やすのは別 Issue（`docs/project/reception-hours-yield-2026-08.md` では、公式サイトに書いてある寺社が 3〜5 割）
- **ページの薄さ**: 写真のある寺社のページも、中身は Commons の写真と住所が中心。新しいドメインの 777 ページのうち Google が索引に入れるのは一部かもしれない。H-12 から 4〜8 週あと、Search Console の「ページ」で「クロール済み - インデックス未登録」が半分を超えるなら、載せる寺社を絞るか中身を足す（別 Issue）
- **第2弾の写真（89 枚）**: #320 の本番の手順（R2 に置く）が済んでいないと、その寺社のページの写真が出ない（浅草寺・竹駒神社を含む）。H-1 で止める
- **変換の数**: Google などのクローラーが寺社のページの写真を月に一度読むと、幅 1200 の変換が最大 777/月（アプリの帯と同じ URL なので、アプリで表示された分とは重ならない）。御朱印の 400 / 1200 と合わせて月 5,000 の無料枠に入るかを、Cloudflare の Images の使用量で月に一度見る
- **OGP の画像が webp**: 寺社のページの `og:image` は webp。LINE など一部のサービスで共有の画像が出ないかもしれない（確かめていない）。出ないなら JPEG の変換（新しい変換の種類が増える）か、`ogp.png` に戻すかを決める
- **証明書が出るまでの間**: H-8 で独自ドメインを入れると、`kaiwa-jun.github.io/goshuin-app/…` は即座に `goshuinsanpo.com` へ転送され、証明書が出るまで HTTPS がエラーになりうる。App Store の審査中は避ける
- **Cloudflare のプロキシを後でオンにしない**: オンにすると GitHub の証明書の更新が失敗し、Cloudflare の AI のクローラーを塞ぐ設定がかかりうる
- **`develop` の push のたびに出る**: アプリの変更だけの push でも作り直して出す（1 分前後）。生成物は同じなので見た目は変わらない
- **Apple のバッジの決まり**: 高さ 48px・余白 1/4 は、Apple の決まりの最小より大きい値として選んだ（実装する人が Apple の今の決まりを読み、食い違えば契約を直す）
- **スクショに写る記録**: ストアと同じく、オーナーのアカウントの実際の参拝先が写る（1.2.0 のときにオーナー了承済みの撮り方）。3 枚目のあゆみの数字はストアと同じ見本の数字
- **撮影者の文字**: Commons の表示のまま（`No machine-readable author provided…` もそのまま出る。アプリの帯と同じ）
- **beacon の `integrity`（SRI）**: Cloudflare の手で入れる snippet は版の無い `beacon.min.js` で、中身は Cloudflare が更新する。`integrity` を付けると更新のたびに読み込めなくなり計測が止まるので、付けない（Cloudflare の配る形のまま）。代わりに、外から読む script はこの1つだけにする（UI-10 で確かめる）
- **確かめていないこと**: GitHub が `www` を直下へ転送すること・`kaiwa-jun.github.io/goshuin-app/` の転送が 301 であること・App Store Connect のキャンペーンの画面の場所・Cloudflare Web Analytics の画面の名前は、どれもこの契約を書いた時点で実物で確かめていない（H-0・H-10 で確かめる）
- **申し送り**: `CLAUDE.md` のアーキテクチャの節に `site/` を足すか（リーダー）。`gh repo edit Kaiwa-Jun/goshuin-app --homepage https://goshuinsanpo.com`（今は `goshuin-app.vercel.app`）をするか（リーダー）
