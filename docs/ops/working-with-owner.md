# オーナーとのやりとりの決まりと、これまでの教訓

2026-10-17 時点。これまでにオーナーから言われたこと・つまずいたことをまとめた。日付はそのことが決まった日。

## 1. 報告のしかた

- **日本語で書く**（2026-10-11。英語で報告したら「日本語でお願い」と言われた）
- 専門用語を避け、ふだんの言葉で書く
- **報告の先頭に「ユーザーに求めること」を書く。** 無ければ「ありません」と書く
- **確かめられなかったことは、確かめられなかったと書く。** 推測で「できた」と書かない
- **進み具合は ✅ / ⬜ のリストで**（2026-10-11）。この後やることを並べ、済んだら ✅ を付けて出し直す
- **PR や Issue は番号だけで言わない**（「239ってなんだっけ？」と言われた）。「PR #335（寺社の確かめの記録）」のように中身を添える
- 長い報告やオーナーに選んでもらうことは、これまで claude.ai のページ（報告と承認）にまとめていた（2026-10-10 の指示）。Claude Code が運用する間は、ここに積む。別の担当はこのページに書けないので、そのときはどこにまとめるかをオーナーに聞く

## 2. オーナーに作業を頼むとき

- **頼む前に、自分の道具でできないかを確かめる**（2026-10-04、「それは私の作業？あなたできるのでは？」と言われた。審査の公開のしかたは API で変えられた）
- オーナーにしか頼めないのは: 鍵を入れること・実機での確認・ストアに出すか公開するかの判断・ブラウザのログイン
- 手順は 1 つずつ、**「どこで（ターミナル／ブラウザのどの画面）・何を打つ・正しい結果・違ったら止める条件」**で書く。オーナーは書いたとおりに正確に打つので、曖昧だと書いたとおりに間違える
- ターミナルのコマンドに `!` を付けない（zsh では結果が反転する。2026-09-27 に migration の記録が走らなかった）
- 貼ってよい出力と、貼ってはいけないもの（鍵・合言葉）を先に書く
- 画面の場所の説明は、公式の説明で確かめてから書く。それでも違ったらスクショを頼む

## 3. 時間と画面

- **平日の 22 時より前は、ブラウザやシミュレータをオーナーの画面に出さない**（2026-10-13）。土日も同じく 22 時台にそろえている（土日の昼間がよいかは聞いていない）
- 画面に出ないもの（API・ファイル・git・DB を読む）は昼間もよい
- `supabase` のコマンドは、打つたびにオーナーの画面にキーチェーンの許可の窓が出ることがある。打つ前に何回出るかを伝え、省けるものは打たない

## 6. アプリを作り変えるときの好み（開発をする場合）

運用の仕事ではないが、機能や画面に手を入れることになったら、次を守る。

- 見た目が主題の変更は、作る前にデザインを起こして合意を取る（受入基準を全部満たしたのに「デザイン的にダメ」でお蔵入りになったことがある）
- 試作は、実装で使える素材だけで作る（HTML で簡単に書ける形に引きずられない）
- 動きは「御朱印帳」の比喩（束ねる・めくる・蛇腹・朱印を捺す）の案を混ぜ、動く試作で並べて選んでもらう。出し方は**おしとやかに**（勢い・回転・弾みを入れない）
- 画面の言葉に、作る側の言葉（追加・登録・マスター・確認待ち）を出さない。「探す」にそろえる
- ストリーク・毎日のプッシュ・ランキングは入れない（「SNS なし・広告なし・静か」が立ち位置）
- 状態の管理にライブラリを足さない、など開発の決まりは `CLAUDE.md`
- 紹介動画を作るなら、オーナーが「いい」と言った Plainwalk の紹介動画の形（1 場面 4 秒・太字 2 行の見出し・地図が描かれていく・数が増える・「〜も、白紙から。」で締める）を下敷きにする
