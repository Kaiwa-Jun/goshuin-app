## ポジショニング（2026-08 市場調査より）

市場は「SNS型の大手（ホトカミ 月間140万人・★4.3 だが重い/広告/UI過密）」と「記録特化の無料アプリ（品質が低い・★3.8）」に二極化しており、**「SNSなし・広告なし・高速で美しい記録特化」は実質空席**。本アプリはこの空席を取りにいく。

- コンセプト文は現行の「集めるたび、地図があなたの旅になる。」を維持
- 抵抗が強いのは「御朱印そのもののデジタル化（紙の代替）」であり、「参拝記録のデジタル化」は広く受容済み。**紙の御朱印の代替を謳う機能は作らない**
- ブーム牽引層は20〜30代女性。「SNS疲れしたが静かに記録したい、でもシェアもしたい」の両面性を前提に、SNS機能は持たず公開/共有は控えめに保つ

### Phase 1: 記録体験の磨き込み（新ハーネスの実戦投入を兼ねる）

「静かな御朱印帳」路線でコア体験を磨く。インフラ追加が不要な UI 中心の作業のため、刷新した自律開発ハーネス（Maestro E2E 含む）の実戦テストを兼ねる。

- 御朱印帳らしい質感の閲覧 UI（見開き・めくり体験）
- 記録フローの最短化（起動から記録完了までのタップ数削減）
- パーソナル年報（あなたの参拝の一年を振り返る）

### Phase 2: 限定御朱印ウォッチャー MVP + サブスク導入（収益化の本丸）

ユーザーが毎日手動でやっている「寺社ごとの SNS/公式サイト巡回」を AI が代行する。競合は人力の編集特集でしか実現できておらず、モデルコストの低下（Haiku 4.5 / Sonnet 5）で個人開発でも運用が現実的になった領域。

- スポットごとの情報ソース登録（公式サイト / SNS URL）。ランク上位スポットから整備
- Supabase Edge Functions の定期実行で巡回 → 月替わり・限定御朱印情報を構造化（`extract-spot-info` の拡張）
- 行きたいリスト・よく行くエリアに応じたプッシュ通知（expo-notifications 導入）
- IAP 導入（RevenueCat 等を比較検討）。**通知系のみサブスク**、押し売り UI は作らない

### Phase 3: 巡礼・ルート計画 + 巡礼パック（買い切り）

- 近くの寺社をまとめて回る計画・ルート化
- 霊場データの整備（**データ未整備のまま課金するのが競合最大の不満要因**。パック公開はデータ検証済みのものに限る）
- Issue #82 Phase 3 の巡礼パック買い切り（300円/パック）と接続

### Phase 4: インバウンド英語対応

英語圏向け goshuin 記録アプリはほぼ空白。i18n 基盤 + 英語ストアページ。規模的に実質別プロダクトのため最後。

## 収益マッピング

| 区分                     | 内容                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------- |
| 永久無料                 | 記録・地図・ギャラリー・コレクション・バッジ（コア体験は一切制限しない — Issue #82 の原則を維持） |
| 買い切り（480〜980円）   | 統計・分析強化、CSV/PDF エクスポート、テーマ・アイコン、御朱印帳風 UI の拡張                      |
| 買い切り（300円/パック） | 巡礼パック                                                                                        |
| サブスク（月200〜300円） | 限定御朱印ウォッチャー通知（AI 巡回のランニングコストを回収）                                     |
| 応援課金                 | お賽銭的な投げ銭（100/300/500円）。Phase 3 以降に検討                                             |

サブスクを通知系に限定する理由: 記録機能への月額課金は「月1〜2回の利用で重い」として一度撤回済み（Issue #82）。月替わり情報の通知は毎月新しい価値が発生するため、唯一サブスクが正当化できる。

## 開発フロー刷新の方針（別途ハーネス設計で詳細化）

2026年の Anthropic 公式知見（Effective harnesses 2025-11 → Harness design for long-running apps 2026-03、Opus 5 プロンプトガイド）に基づき、既存ハーネスを以下の方向で刷新する:

1. **最小ハーネス原則**: 現行 CLAUDE.md の Phase 1→1.5→2→2.5→3 の多段フローを軽量化。中規模タスクは単一パス、Evaluator 投入は複雑度で判断
2. **Opus 5 世代への指示反転**: 「必ず検証しろ」系の強制指示を削除（過剰検証の原因）。サブエージェント委譲にはキャップを設定
3. **ネイティブ機能への移行**: 自前の並列化・進捗管理を background subagents / `isolation: worktree` / checkpoints に置き換え
4. **ネイティブ E2E の導入（最大の欠落）**: Playwright + Expo Web では地図・カメラ・位置情報・サインインが検証できない。Maestro 等のモバイル E2E を導入し、自律ループの検証基盤にする
5. **契約 + feature list 駆動**: 実装前に機械チェック可能な成功条件（契約）をファイル化し、Generator は契約に対して実装、Evaluator は契約に対して検証
6. **モデル分担**: Fable 5 = リード/プランニング、Opus 5 = 実装 Generator、Sonnet 5 = Evaluator・並列ワーカー
7. **人間ゲートは PR 直前のみ**: それ以外は auto mode + hooks（決定論的ルールは hook で強制）

刷新時に既存の陳腐化ドキュメント（roadmap.md / monetization.md / CLAUDE.md の `src/stores` 記述）も整理する。
