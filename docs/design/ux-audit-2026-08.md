## A. ユーザー指摘の検証

### 地図 > 御朱印を記録

#### A-1. 「カメラで撮影」でカメラが起動しない（バグ）

**該当**: `src/components/record/PhotoPickerModal.tsx:21-26`

```ts
const handleCamera = async () => {
  const result = await ImagePicker.launchCameraAsync(pickerOptions);
  ...
};
```

**原因候補**（静的解析では確定不可。実機検証が要る）:

1. **権限リクエストが無い** — `requestCameraPermissionsAsync()` を一度も呼んでいない。カメラは iOS で明示的な許諾が必須（フォトライブラリは PHPicker のため不要）。**ギャラリーだけ動いてカメラが無反応という症状と最も整合する**
2. **try/catch が無い** — 例外が unhandled promise rejection になり、UI 上は「何も起きない」
3. モーダルを閉じずに起動 — `Modal.tsx:39` は native の `RNModal` なので iOS の modal-on-modal に該当しうる。ただしギャラリーが同じモーダルから動く以上、主因ではない可能性が高い

`app.json` の `NSCameraUsageDescription` は設定済みなので、クラッシュではなく権限拒否のパスに落ちている。

**対応**: 権限リクエスト追加 + try/catch + 拒否時に設定への導線 + 起動前にモーダルを閉じる（衛生的な対処として）
**規模**: S ／ **要**: 実機での再現確認

#### A-2. 訪問日が西暦のみ → 和暦対応

**該当**: `src/screens/RecordScreen.tsx:52`

```ts
const formattedDate = `${form.visitedAt.getFullYear()}年${...}月${...}日`;
```

御朱印の墨書きは和暦が主流という指摘は妥当。**保存は現状のまま（ISO/西暦）で、表示層だけ和暦にするのが安全**:

```ts
new Intl.DateTimeFormat('ja-JP-u-ca-japanese', {
  era: 'short',
  year: 'numeric',
  month: 'long',
  day: 'numeric',
}).format(date); // → 令和8年8月8日
```

> ⚠️ Hermes（Expo の既定 JS エンジン）の `Intl` は部分実装で、**`japanese` カレンダーが使えない可能性がある**（特に Android）。実装時に要検証。非対応なら「令和 = 年 - 2018」の変換ユーティリティ（10行程度）で代替できる。

**規模**: S
**論点**: 記録画面だけか、ギャラリー・スポット詳細も含めて全体を和暦にするか。併記・トグルにするか

#### A-3. 日付ピッカーのスクロール位置

**該当**: `src/screens/RecordScreen.tsx:134-153`

iOS は `display="inline"` でカレンダーが ScrollView の流れの中に展開されるが、**開いた時の自動スクロールが無い**ため画面外に出る。

注目すべきは、**同じファイルの `168-175` 行でメモ欄が既に同じ問題を `scrollTo` で解決している**こと:

```ts
onFocus={() => { setTimeout(() => {
  scrollViewRef.current?.scrollTo({ y: memoLayoutY.current, animated: true });
}, 300); }}
```

日付側に同じパターンを適用するだけで解消する。より確実にするならカレンダーをモーダル/ボトムシート化する選択肢もある。

**規模**: S

#### A-4. 投稿時の「アップロードエラー」

**該当**: `src/screens/RecordScreen.tsx:77-79` / `src/services/stamps.ts:30-51`

```ts
const errorType = isNetworkError(result.error) ? 'network' : 'upload';
navigation.navigate('Error', { type: errorType, origin: 'record' });
```

**原因は静的には特定できない**。決め手になる `error.message` を、コードが投げた直後に捨てているため。

候補:

- Storage の RLS ポリシー / バケット設定 — **`goshuin-images` バケットとポリシーが `supabase/migrations/` に一切存在しない**（ダッシュボードで手作業作成とみられる）。環境再現性の穴でもある
- 認証セッションの状態
- `formData.append('', {...})` という空フィールド名の FormData 方式が Expo SDK 54 / supabase-js の現行版で通らなくなった可能性

**対応順序**: ①エラー原文を画面かログに出す ②再現して切り分け ③修正
**規模**: 診断 S ／ 修正は原因次第

### 地図 > 検索（ボトムシート）

#### A-5. 初期表示と展開時の情報設計

**該当**: `src/components/spot-detail/SpotBottomSheet.tsx:175-207`

構造上の問題が指摘の背景にある:

```tsx
{mode !== 'expanded' && <SpotCompactCard ... />}
{mode === 'expanded' && <ScrollView><SpotDetailContent ... /></ScrollView>}
```

**compact と expanded で別コンポーネントに丸ごと差し替わる**。共通ヘッダーが無いので、展開時に内容が「差し替わった」ように飛ぶ。段階的に情報が増える（progressive disclosure）形になっていない。

- スナップは 2段階のみ（compact は `COMPACT_HEIGHT = 240` 固定 / expanded は画面の 0.85）
- 中間スナップが無い
- 240px 固定なので、限定御朱印が多いスポットでは compact 内で情報が切れる

ユーザー提案の要素整理は妥当。加えて**「共通ヘッダー + 下に段階的に足す」構造への変更**を併せて検討したい。

**規模**: M

#### A-6. 神社/寺バッジが1行を占有している

**該当**: `src/components/spot-detail/SpotCompactCard.tsx:36-50`

現状は縦に3行 + 右にフラグ:

```
📍 住所
```

指摘通り、名前・バッジ・フラグは1行に収まる。240px 固定高の中で1行分空くので、そこを画像や他の情報に使える。

**副次的な発見**: 展開側（`SpotDetailContent.tsx:86-97`）は**バッジが名前の上**にあり、compact と順序が逆。一貫していない。

**規模**: S

#### A-7. 「御朱印を記録」がテキストリンクで弱い

**該当**: `src/components/spot-detail/SpotDetailContent.tsx:110-113`、スタイルは `218-227`

```ts
recordLink: { flexDirection: 'row', alignItems: 'center', gap: spacing.xs, marginBottom: spacing.xl },
```

背景・枠・padding が無いアイコン+テキスト。**タップ領域が推奨の 44pt を下回っている**とみられ、見た目の弱さだけでなく操作性の問題でもある。

さらに `SpotCompactCard` には存在せず**展開しないと出てこない**。アプリのコア動作の入口としては深すぎる。

**規模**: S〜M

#### A-8. ボトムシートに画像がほしい

**現状**: 展開時には**既に画像グリッドがある**（`SpotDetailContent.tsx:115-139`。自分の記録 + 他ユーザーの公開御朱印）。無いのは compact 側。

つまり実質の要望は「**compact にサムネイルを1〜3枚出す**」。

**ただし懸念が2つ**:

- リリース直後は公開御朱印がほぼ0件なので、多くのスポットで空白が目立つ
- 外観写真のデータソースが無い（`spots` に画像カラムが無い）

**論点**: 画像の供給源をどうするか（ユーザー投稿のみ／限定御朱印の投稿画像を流用／外部データ）。供給が細い間の空状態デザインもセットで要る

#### A-9. 未訪問ピンのグレーが寂しい

```ts
pin: { shrineVisited: '#EF4444', templeVisited: '#A855F7',
```

**これは ui-design v6 の仕様通り**（「未訪問: グレー gray-400 / 12px」）。意図は訪問済みを目立たせるコントラスト設計。ただし**初期状態ではほぼ全ピンがグレー**になるため、「寂しい」という反応は設計意図の副作用として妥当。

#### A-12. フラグの意味が「行きたい」か「行った」か分かりにくい

- アイコン単独をやめてラベルを付ける

## B. こちらで見つかった追加の論点

### B-1. コアバリュー「3タップで記録完了」が守れていない

ui-design v6 のコアバリュー筆頭。実際の最短経路（ログイン済み・スポット自動選択が効く場合）:

```
FAB → 「写真を追加」 → 「カメラ/ギャラリー」 → 写真選択 → 「この内容で記録する」 → 確認モーダル「登録する」
```

システム UI 内の操作を除いても**5〜6タップ**。特に最後の `ConfirmModal` が1タップを足している。

**論点**: 確認モーダルを廃し、「記録後に Undo できる」方式に変えるか。誤登録防止の価値とコアバリューのトレードオフ。

### B-2. 記録の入口が地図に集中している

入口は 2つだけ:

- `MapScreen.tsx:440` の FAB
- スポット詳細 / ボトムシート（`SpotDetailScreen.tsx:31`）

**御朱印タブとコレクションタブからは記録に入れない**。アプリのコア動作なのに、4タブ中2タブが入口を持たない。A-10 はこの一部が症状として出たもの。

### B-3. エラーの握り潰しがコード全体の作法になっている

- `RecordScreen.tsx:78` — `error.message` を捨てる
- `services/spotInfo.ts:11,26` / `services/stamps.ts:23,89` ほか — `console.warn` して `[]` を返す

結果として、**通信失敗と「データが0件」が画面上で区別できない**。ユーザーは壊れていることに気づけず、こちらもログ無しでは診断できない（A-4 がまさにこれ）。

**方針**: コア導線（記録・アップロード）はエラー種別と原文を出す。一覧系は最低限「読み込めませんでした / 再試行」を出す。

### B-4. ui-design v6 と direction v2 が矛盾している

- v6 `4.7`: ギャラリーは「**無料版制限: 直近20件のみ表示**、プレミアム誘導バナー」
- direction v2: 「記録・地図・ギャラリー・コレクションは**永久無料**（コア体験は一切制限しない）」

実装は制限なし（= direction v2 に沿っている）。**設計書だけが撤回済み方針のまま**。UI 設計書の改訂が要る。

### B-5. 御朱印帳テーブルが未使用のまま存在している（P1-03 に直結）

`supabase/migrations/20260208102601_create_goshuincho.sql`:

```sql
CREATE TABLE public.goshuincho (
  id UUID PRIMARY KEY, user_id UUID NOT NULL, name TEXT NOT NULL,
  cover_image_path TEXT, started_at DATE, is_default BOOLEAN, ...
```

さらに `20260208105312_add_default_goshuincho_on_signup.sql` でサインアップ時にデフォルト行まで作っている。**しかし UI が一切無い**。

v6 の「将来画面 15/16（御朱印帳一覧・詳細）」がこれに対応する。**P1-03 はスキーマが既にあるぶん、見た目の印象より着手コストが低い可能性がある**。

### B-6. コレクションタブの中身が混在している

セクション構成: 獲得バッジ / 巡礼チャレンジ / 地域別 / **行きたいリスト**

前3つは「実績（過去）」だが、**行きたいリストだけ「計画（未来）」**。時間軸が逆のものが同居している。A-12 のフラグ曖昧問題と根が同じ。

### B-7. 受付時間は「仕組みはある、データが無い」（2026-08-09 訂正）

> ⚠️ **当初この項目を「カラムが無いので UI ではなくデータ取得の課題」と書いたが、これは誤りだった。**
> `spots` テーブルだけを見て `spot_aggregated_info` を見落としていた。以下が正しい状況。

**仕組みは既にある**:

- `spot_aggregated_info` に `info_type = 'reception_hours'`（`{open, close, notes}`）を保存する経路がある（`useSpotInfo.ts:27`）
- `SpotInfoSection.tsx:26-33` が「受付 9:00〜17:00」の形で**既に描画している**
- しかも `SpotCompactCard.tsx:56` 経由で、**既に compact に出ている**
- 該当データが無ければ `SpotInfoSection.tsx:40` が `null` を返すため、間延びもしない

**足りないのはカバレッジだけ**（本番 DB 実測、2026-08-09）:

| info_type           | 行数  |
| ------------------- | ----- |
| limited_goshuin     | 15    |
| parking             | 3     |
| **reception_hours** | **2** |
| affiliated_shrines  | 1     |
| access_notes        | 1     |

全1,109スポットのうち受付時間があるのは**2件**。つまり「UI に出す」作業は不要で、**データを増やす**作業だけが残っている。

供給源の候補: ①ユーザーのメモから抽出（`RecordScreen.tsx:180-183` のメモガイドが既にこれを示唆している。`extract-spot-info` が実装済み）②クローラの拡張（限定御朱印と同じ仕組み）③手動整備

**規模**: M（UI 実装は不要。データ整備のみ）

### B-9. 地図のクラッシュは既知（新規ではない）

「マップを操作していると落ちる」は **P1-07（地図の全国スケール表示の恒久解禁）** として既知。Apple Maps のタイルメモリ起因とみられ、現在は `minZoomLevel=8` で封じ込め中。アプリコード側（マーカー churn / スナップショット / アニメリーク）は Issue #099 の追補1〜3で対処済み。

### B-10. オンボーディングの見た目が弱い（2026-08-11 追記・ユーザー指摘）

## C. 画面構成（IA）の再考

現状: **地図 / 御朱印 / コレクション / 設定**

観察された構造的な問題:

1. 「御朱印」= 自分の記録グリッド、「コレクション」= 実績 + 計画 → **どちらも「自分の記録」**で、ユーザー視点の境界が曖昧
2. 「設定」は利用頻度が低いのに常時1枠を占有（中身は3セクションのみ）
3. **コア動作である「記録」にタブが無く**、地図上の FAB に依存（B-2）

### 案1: 現状維持 + 整理

4タブのまま。行きたいリストを地図側へ寄せ、御朱印タブに記録導線を足す。

- ✅ 変更が小さい／既存の学習を壊さない
- ❌ 「御朱印」と「コレクション」の境界の曖昧さは残る

### 案2: 3タブ + 中央に記録ボタン

**地図 / [記録] / 自分**。設定は「自分」の中へ。御朱印とコレクションを「自分」に統合。

- ✅ コア動作がタブバー中央に昇格 → 「3タップで記録」に最も効く
- ✅ 記録アプリとして一般的な型で学習コストが低い
- ❌ 統合後の「自分」タブの情報量が多くなり、内部の整理が別途要る

### 案3: 御朱印帳を主役に据える

**地図 / 御朱印帳 / 発見 / 自分**。P1-03 の見開き UI をギャラリーの置き換えとして主役に。

- ✅ direction.md の「静かな御朱印帳」路線に最も忠実／差別化が front and center
- ✅ 未使用の `goshuincho` スキーマ（B-5）が活きる
- ❌ 変更が最も大きい／P1-03 の完成が前提になる

### なぜ形を変えないのか

`issue-099` の追補2で**クラスタは `Marker` の `image` prop に移行済み**で、**個別ピン（`SpotMarker`）の画像化は「実機クラッシュが残った場合の次の一手」として温存**されている。形やサイズを変えると、将来ピンを画像化するときのアセット種類が増える。

**色だけなら追補の制約にほぼ抵触しない。** `SpotMarker` は View 合成で、`backgroundColor` を差し替えるだけならレンダリングコストは不変。

- `src/theme/colors.ts` の `pin.unvisited`
- 色を決めている2箇所: `src/screens/MapScreen.tsx:51-54` / `src/screens/PilgrimageDetailScreen.tsx:90-92`
- 規模: **S**

⚠️ トレードオフを承知の上での決定: 現行のグレーは「訪問済みを目立たせる」ための設計で、未訪問に色を付けると訪問済みが相対的に埋もれる。淡さの度合いで調整する。

## D-6 の決定（2026-08-11）

**受付時間は「調査してマスタデータとして持つ」。ただし全件やる前に歩留まりを測る。**

| 項目              | 決定                                                                            |

| 収集              | **Claude が実施**。公式サイト（限定御朱印と同じ情報源が使えるものはそれを使う） |
| 更新運用          | **取得日を持ち、UI に併記する**（案①）                                          |

| メモガイド文言    | **案A: 「受付時間」だけ文言から外す**                                           |

### ⚠️ 規模の訂正: rank5+4 は 949件（「29スポット」ではない）

本番 DB 実測（2026-08-11）:

| rank | 件数    |
| ---- | ------- |
| 5    | **469** |
| 4    | **480** |
| 3    | 103     |
| 2    | 19      |
| 1    | 38      |

**「29スポット」は東京・宮城・京都の rank5 だけ**で、これはクローラの巡回対象の話だった。全国の rank5 は469件ある。さらに**公式サイトの URL を持っているのはその29スポットだけ**（`spot_info_sources` に79ソース）で、残りはサイト探しから始まる。

### 段階実行（合意済み）

1. **まず URL がある29スポットで回して取得率を測る**（1日かからない）
2. **7〜8割取れたら rank5 全件へ**
3. **3割なら方針を考え直す**

御朱印の受付時間は公式サイトに載っていないことがそれなりにある。949件やってから歩留まりが低いと分かるのは避ける。

### 更新運用（案①）

- seed に **`collected_at`** を持たせる
- 詳細画面に「受付 9:00〜17:00**（2026年8月時点）**」と小さく併記する
- 古くなるリスク自体は消せないが、**嘘をつかない形にはできる**
- 再取得は年1回程度の手動バッチで足りる（cron には載せない）。**今回はスコープ外**

### seed とメモの優先順位 — 実装不要

`extract-spot-info`（`supabase/functions/extract-spot-info/index.ts:220-223`）の受付時間の集約は**すでに "Latest wins"**。

```ts
case 'reception_hours': {
  // Latest wins
  aggregatedData = relevantStamps[0].extracted_info[infoType];
  break;
}
```

つまり seed した行は**誰もメモに書かなければ残り**、誰かが書けば**その時点で上書きされる**。希望する挙動がそのまま既存実装で成立するため、**優先順位のためのコード変更は不要**。

⚠️ 留意点: `spot_aggregated_info` は**スポット単位でグローバル**なので、1人のメモが全ユーザーの表示を書き換える。ユーザーが増えたら見直す論点（今回はスコープ外）。

### メモガイドの文言（案A）

現行（`src/screens/RecordScreen.tsx:272-275`）:

> 駐車場の有無、**受付時間**、アクセス情報などを書くと、
> スポット情報として自動的に反映されます

→ **「受付時間」だけ外す**。丸ごと消すと**駐車場とアクセス情報の供給源も同時に消える**ため（本番でそれぞれ **3件 / 1件**しかなく、メモが唯一の入り口）。

### 前提として押さえておくこと（監査本文の B-7 に無い事実）

**パイプラインは end-to-end で実際に動いている。** 未実装でも故障でもない。

```
記録を保存 → useRecordForm.ts:165 が triggerExtraction(stamp.id)
  → extract-spot-info が【メモの本文】を Claude に渡す
  → parking / reception_hours / affiliated_shrines / access_notes を抽出
  → stamps.extracted_info に保存 → spot_aggregated_info に集約
  → SpotInfoSection が「受付 9:00〜17:00」と描画
```

**データが2件しかないのは入力がユーザーの手書きメモだから**で、ユーザーが実質いないため供給が立ち上がっていない。B-7 の「データ整備のみが残っている」は正しいが、その原因までは書かれていなかった。
