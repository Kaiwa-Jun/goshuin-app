**結論から: 取得率は 46%（13/28）。御朱印と明記された時間に限ると 29%（8/28）。**
D-6 が定めた判断基準「7〜8割なら rank5 全件へ / 3割なら方針を練り直す」に照らすと、**下限側**。
**rank5 全件（469件）への展開はこのままでは推奨しない。** 判断はユーザー。

## 1. 何を測ったか

D-6 の決定（`docs/design/ux-audit-2026-08.md`「D-6 の決定」）の段階1:

> まず URL がある29スポットで回して取得率を測る

実際に `spot_info_sources` に `source_type='official'` を持つのは **28スポット・40 URL**（29ではなかった。1件は `sns_link` のみ）。この28件を対象に、公式サイトから御朱印の受付時間を収集した。

**手順**: ①seed 済みの公式 URL を取得 → ②取れなければ同一サイト内の御朱印ページ・案内ページを当たる（最大2巡）。
**手作業でのページ探索は意図的に浅くした。** 469件へ展開するときに人手で探すことはできないので、深く探すと歩留まりを過大評価する。

## 3. この数字をどう読むか — 4つの所見

### ⚠️ 所見1: この28件は「最良のサンプル」なので、全体の歩留まりはこれより下がる

28件は**公式サイト URL が既に判明している**スポット。rank5 の残り441件（469 − 28）は**サイト探しから始まる**ため、URL 特定の失敗分だけ確実に目減りする。**46% は上振れした数字**として扱うべき。

### ⚠️ 所見2: 「御朱印の専用ページがある = 時間が書いてある」ではない

取れなかった14件のうち **4件は専用の御朱印ページを持っているのに時間の記載が無い**:

- 東寺 `/nokyosho/`（納経所のページ）
- 大崎八幡宮 `/gosyuin/`
- 志波彦神社・鹽竈神社 `/about/goshuin.html`
- 烏森神社 `/御朱印`

**「御朱印ページを見つけられれば取れる」という前提は成り立たない。** クロール対象を広げても歩留まりは伸びにくい。

### ⚠️ 所見3: 参拝者の多い大社・大寺ほど書いていない

記載が無かった14件には伏見稲荷大社・清水寺・金閣寺・上賀茂神社・下鴨神社・靖國神社・神田神社・増上寺が並ぶ。**アプリの利用者が最も行きそうなスポットほど埋まらない**という、価値の面で不利な偏り方をしている。

### ⚠️ 所見4: proxy を採ると「嘘をつかない」方針と衝突する

proxy 5件は社務所・授与所・祈祷受付の時間であって、御朱印の受付時間ではない。**実際より広い時間を出す危険がある。**

最も分かりやすいのが湯島天満宮で、社務所は 9:00〜19:00 だが**授与は 17:00 で終わる**。proxy をそのまま `{open, close}` に入れると「受付 9:00〜19:00」と表示され、**18:00 に行った利用者は閉まった窓口の前に立つ**。

D-6 は「古くなるリスクは消せないが、嘘をつかない形にはできる」を方針にしていた。proxy を混ぜるなら、**出典を文言に出すこと**が最低条件（後述）。

## 4. 実装面で分かったこと（コード変更が不要な2点）

### ✅ 取得日の併記は実装不要 — `notes` が既に括弧で描画される

D-6 の着手手順は「3. `SpotInfoSection` に取得日の併記を足す」としていたが、**既に実装されている**。

`src/components/spot-detail/SpotInfoSection.tsx:26-33`:

```ts
if (receptionHours) {
  let text =
    receptionHours.open && receptionHours.close
      ? `${receptionHours.open}〜${receptionHours.close}`
      : '時間情報あり';
  if (receptionHours.notes) text += `（${receptionHours.notes}）`;
  items.push({ icon: 'schedule', text: `受付 ${text}` });
}
```

`info_data.notes` に `2026年8月時点・公式サイト` と入れれば **「受付 9:00〜17:00（2026年8月時点・公式サイト）」** がそのまま出る。型（`src/types/supabase.ts:36`）も `{ open?, close?, notes? }` で `notes` を許容済み。

**これは "Latest wins" と同じパターン**（D-6 で seed とメモの優先順位もコード変更不要と分かった件）。**D-6 の残り作業は seed SQL を書いて流すことだけ**になる。

### ✅ seed 行がメモに消される心配はない

`extract-spot-info` は `spot_aggregated_info` に対して **UPSERT しかしない**（`index.ts:251`。delete は1箇所も無い）。メモが来なければ seed 行はそのまま残り、来れば "Latest wins" で上書きされる。D-6 が望んだ挙動が既存実装のまま成立する。

### ⚠️ ただし `{open, close}` では 13件中4件が表現できない

| スポット   | 表現できない理由                                                                    |
| ---------- | ----------------------------------------------------------------------------------- |
| 明治神宮   | 終了が「閉門まで」＝月ごとに変わる                                                  |
| 瑞巌寺     | 最終受付が季節で4段階（4-9月 16:30 / 10・3月 16:00 / 11・2月 15:30 / 12-1月 15:00） |
| 浅草神社   | 平日と土日祝で異なる                                                                |
| 湯島天満宮 | 社務所と授与で終了時刻が違う                                                        |

**きれいに `{open, close}` に収まるのは 9/13。** 残り4件は `notes` に逃がす（下記 seed SQL はその方針で書いてある）。スキーマを変えずに済むが、**構造化データとしての質は落ちる**（「17:00 までに行けば大丈夫か」を機械的に判定できない）。

### ⚠️ 既存のメモ由来データと1件ぶつかる（宮城縣護國神社）

本番の `reception_hours` は現時点で2件あり、うち**宮城縣護國神社はメモ由来の行が既にある**:

|      | 既存（メモ由来）            | 今回の収集（公式サイト）             |
| ---- | --------------------------- | ------------------------------------ |
| 時間 | 9:00〜**17:00**             | 9:00〜**16:00** 頃                   |
| 出所 | ユーザーのメモ（stamp 1件） | `gokokujinja.org/kitou/goshuin.html` |
| 日付 | 2026-04-01                  | 2026-08-11                           |

**値が食い違っている。** D-6 の決定は「**メモが勝つ**」なので、seed で潰してはいけない。
下記 seed SQL は `on conflict ... where source_stamp_ids = '{}'` で**メモ由来の行を更新対象から外している**（seed 由来の行だけ再実行で更新できる）。

📌 どちらが正しいかは不明。公式サイトの「午後4時ごろまで」という書き方からすると、実際には多少融通が利く可能性がある。**この食い違い自体が、seed を万能の解にできない理由の一例**。

## 5. ⚠️ seed する際の落とし穴: スポット名は一意ではない

`spots` を名前で引くと、**八坂神社が2件・日枝神社が3件**返る（全国に同名社があるため）。名前で seed SQL を書くと**別のスポットに受付時間が付く**。

必ず `spot_info_sources` 経由で公式サイトを持つスポットに紐付けるか、UUID を直書きすること。下記 seed SQL は UUID 直書きにしてある。

## 6. 判断してほしいこと

段階2（rank5 全件 469件への展開）に進むかどうか。3つの案:

| 案                                                 | 内容                                                   | 得られるもの                                               | コスト                                        |
| -------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------- | --------------------------------------------- |
| **A. explicit のみ採用して打ち切り**               | 8件だけ seed し、全件展開はしない                      | 嘘をつかない。8スポットで正確な情報                        | ほぼ無し（seed SQL は下記に用意済み）         |
| **B. explicit + proxy を採用し、出典を文言に出す** | 13件を seed。proxy は notes に「社務所受付時間」と明記 | 13スポット。誤解は文言で防ぐ                               | ほぼ無し（同上）                              |
| **C. rank5 全件へ展開**                            | 441件のサイト探し + 収集                               | 最大で 200件前後（46%）だが**実際はもっと少ない**（所見1） | 大。かつ所見3のとおり主要スポットが埋まらない |

**推奨は B。** 今夜の測定で13件分は既に手元にあり、seed するコストがほぼゼロで、D-6 が求めた「取得日を持ち UI に併記する」も実装不要で満たせる。一方 **C は投下量に対して得られるものが釣り合わない** — 主要スポットほど記載が無く（所見3）、上振れした 46% でも半分は埋まらない。

**受付時間の本命の供給源は、やはりユーザーのメモ**（D-6 の前提どおりパイプラインは動いている）。seed はその立ち上がりまでの当て木として位置づけるのが妥当。
